# LLM natural-language-to-SPARQL evaluation

Generated by `app/llm_sparql.py`. Both systems were run against the live Fuseki endpoint and scored by **executing** their queries and comparing result sets with the verified gold answers in `app/queries.py`. No answer is judged by eye.

- **Model:** `qwen2.5-coder:3b` (open weights, served locally by Ollama)
- **Baseline:** keyword retrieval over the 13 stored competency questions
- **Questions:** 13 SELECT/ASK competency questions
- **Endpoint:** Apache Jena Fuseki 6.2.0

CONSTRUCT and DESCRIBE questions (CQ13, CQ15) are excluded: they return graphs rather than row sets, so set-based scoring would not be meaningful.

## Metrics

| Metric | Meaning |
|---|---|
| syntax | query executed against Fuseki without error |
| exact | result set identical to the gold answer |
| answer F1 | per-row overlap with the gold answer |

Result sets are compared by the **values** in each row, ignoring variable names and row order, because `?title` and `?t` are equally correct choices.

## Diagnosis: why the model fails

The headline number is unflattering, so it is worth saying precisely *what* goes wrong rather than leaving a bare 0/13.

### Most failures are empty results, not broken syntax

12/13 generated queries parsed and executed. The model has clearly learned SPARQL *form*. What it has not learned is this ontology's *shape*.

### The single biggest cause: inference-only vocabulary

Seven properties and eight classes in this ontology are never asserted - they exist only after a reasoner runs: `:authored`, `:references`, `:hasTeachingAncestor`, `:isWithinSchool`, `:createdInLineageOf`, `:criticizes`, `:praises`, and the eight defined classes such as `:TeacherThinker`.

They appear in the schema context, so the model reasonably reaches for them - `:authored` for 'works by', `:TeacherThinker` for 'masters'. Against a plain endpoint those queries are *valid and empty*, which is the worst kind of wrong: it looks like a correct answer of zero.

Measured: **5 of 13** generated queries used at least one inference-only term. Re-running the identical prompts against a materialised endpoint (the OWL-RL closure plus the R1 rule links, 2,735 triples) cut empty results from **8 to 5**.

That is a finding about *system design*, not about the model: if a knowledge graph is to be queried by an LLM, the endpoint should serve the inferred closure, or the inference-only terms should be hidden from the prompt. A human query author hits the same trap.

### The remaining errors are genuine comprehension failures

Materialisation does not rescue the rest, and those are honest losses at this model scale:

- **Direction confusion.** `:fromWork` used where `:toWork` is meant, so 'works criticised by X' returns the critics instead.
- **Type errors.** `?w :title :CritiquePureReason` treats an IRI as a string literal.
- **Dropped projections.** 'Which cities do philosophers belong to' answered with cities only, omitting the philosopher.
- **Aggregate misuse.** A query placed an aggregate outside its `GROUP BY` and failed to parse.

### What this shows

**Scale did not help.** Going from 3B to 7B parameters changed the exact-match score not at all (0/13 in both cases) and the mean F1 not at all, while making each query roughly six times slower. The larger model also produced *more* malformed queries, not fewer. Whatever is blocking these models, it is not capacity at this scale.

**Materialising inference helped, but only partly.** Serving the OWL-RL closure cut 'empty result' failures for both models, confirming that reaching for inference-only vocabulary is a real and measurable cause. It converted those into 'wrong entities' failures rather than into correct answers: the queries then returned *something*, but still not the right thing.

**The remaining barrier is domain modelling, not SPARQL.** Both models write syntactically valid SPARQL most of the time. What they cannot do reliably is pick the right direction on a reified relation (`:fromWork` versus `:toWork`), decide when a question needs a join through `:Engagement` at all, or notice that `:title` takes a string while everything else takes an IRI. Those are facts about *this ontology*, and no amount of generic code pre-training supplies them.

The practical implication for a production system is that schema-in-the-prompt is not sufficient. The realistic designs are few-shot examples drawn from this ontology's own query log, a fine-tune on question/SPARQL pairs, or constrained decoding against the vocabulary. All three are out of scope here, but the evaluation harness would measure any of them unchanged.

## Reading these numbers honestly

1. **The baseline is strong by construction.** It retrieves from the same 15 hand-written, verified queries the questions were drawn from, so on exact phrasing it is near-perfect. That is the point: it shows what an LLM must beat to be worth adding, rather than flattering the LLM against a straw man.
2. **The LLM's advantage is not on this test set.** Its value is on *unseen* phrasings, where the baseline can only return whichever canned query happens to share the most words. Measuring that properly needs a held-out set of paraphrases, which this evaluation does not yet have.
3. **Scale was tested and did not help.** 7B scored identically to 3B while running six times slower, so these are not simply 'too small a model' numbers.
